# sample-data/

Fictional vendor security documents used to test the application. Generated by [`scripts/generate_sample_data.py`](../scripts/generate_sample_data.py), so anyone can see exactly how each document, including each hidden problem, was made.

**Rules**

- Synthetic data only. No real company, vendor, auditor, person or document is copied or referenced. The auditor "Halvorsen & Pike LLP" is invented.
- Every page and sheet says the document is fictional.
- Some documents contain deliberate problems so the security tests have something to catch. Every problem is listed below and in each vendor's `expected-findings.json`, so nobody mistakes one for an accident.

## Canary tokens

Each vendor's documents carry a unique reference string, such as `CANARY-NIMBUS-7Q2F`. If one vendor's canary ever appears in another vendor's assessment, the system has leaked data between vendors. The cross-vendor isolation test (SR-09) checks for this.

## Expected findings

Each `expected-findings.json` is the answer key: the evidence state the system should reach for every control category, with the source page or questionnaire row. It is used to:

- test the rules engine (the same evidence states must always produce the same score), and
- measure AI extraction accuracy against a known answer (NIST AI RMF "Measure"), starting in Phase 5.

## A finding already

Copperline scores **80 (Critical)** because it only sent self-attested answers: eight "unverified" categories alone add 48 points. That may be too harsh for a vendor whose only problem is missing evidence, and a Critical rating triggers the two-person review rule. This is an open policy question, with options, in section 9 of the [scoring methodology](../docs/risk-management/scoring-methodology.md).

## Regenerating

```bash
python3 -m pip install -r requirements-dev.txt
python3 scripts/generate_sample_data.py   # rebuild the documents
python3 scripts/verify_sample_data.py     # check the committed files match
```

The content is deterministic: every page's text, every cell and all metadata come out the same on every run. The exact bytes can differ between computers because compression libraries differ, so the automated check compares content, not bytes. It runs on every pull request, so a test document can't be changed, or have its hidden injection removed, without the change showing up.
